------------------------------------------------------------------------
THE FORTY MINUTES THIS RUN COST, AND WHAT CAME OUT OF IT
------------------------------------------------------------------------

The first pass reported 57 passed / 3 failed / 17 SKIPPED - nine more skips
than the baseline, which reads as a serious regression. It was not one.

All nine carried the same message: the target window could not be brought to
the front, "Windows refuses SetForegroundWindow to a process without
foreground rights, and this harness is a background process." That sentence is
TRUE and it is also the message the harness prints when something completely
different is happening. It sent the investigation into the harness: three
raise strategies were probed against a live build (plain SetForegroundWindow,
AttachThreadInput + BringWindowToTop, SW_MAXIMIZE) and all three failed.

The actual cause was found by asking a question the harness had never asked:
WHAT is holding the foreground? A GetForegroundWindow + GetClassNameW said

    class = Open With,  pid 27660 (OpenWith.exe)

A stray "Open With" system dialog, left on the desktop by some earlier action,
holding the foreground the way a system modal does and yielding it to nothing.
One taskkill, and eight of the nine passed immediately.

The ninth was mine: a_shift_drag_between_documents_moves_the_pages skipped
because I had passed --second-pdf curve.pdf, which has ONE page, and a
one-page document cannot be moved out of by design. With big.pdf (5 pages) it
passes. A fixture choice that turns a passing check into a skip is a false
regression too, and it is worth stating that the harness diagnosed this one
itself, in one sentence, naming the remedy.

THE FIX: sys::describe_foreground(), reported at BOTH refusal sites. A refused
raise now names the window that refused it, and says what to do about it:

    THE FOREGROUND IS HELD BY: untitled (window class `Open With`, pid 31884).
    If that is not the application under test and not this harness, it is
    holding the desktop and no retry will help - dismiss it and run again.

FALSIFIED, because a message that has never been seen to fire is not evidence.
A .NET TopMost form was NOT sufficient - it yields the foreground on request,
the check passed, and the message never appeared. The real dialog had to be
reproduced:

    rundll32.exe shell32.dll,OpenAs_RunDLL <a file with no association>

With that on screen the check reported SKIP and named the blocker by class and
pid. That is the only run in which this message has been observed, and it is
the reason it can be trusted.
